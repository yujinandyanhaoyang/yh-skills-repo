# 接口用例失败修复模式（案例库）

沉淀本次会话与历史已证实的失败模式、判定方法与修复动作。按失败特征反查本节，快速对号入座。

## 模式 1：服务正常返回但断言写死数据（B1 断言过脆）

**报错特征**：HTTP 200、业务码 `c=0`、但响应数据为空（`d=[]` / `modelTopics:[]` / `d=null`）；断言期望「必须有数据 / 具体 ID」→ 失败。

**判定**：同账号同环境的其他用例能取到数据（说明服务与账号正常）→ 是该接口查询型返回空；或该账号在该数据域（B 端/某租户）无数据。写死数据必然误报。

**修复**（`update_test_case`）：
- 断言从「Response Data contains: xxx」改为数据无关：`Response Code equals: 200` + jsonPath `$.c == "0"`（或 `$.c==0`，以平台断言格式为准）；
- 保持「接口正常 + 业务成功」的最小校验，SIT 数据怎么变都不误报。

**实例**：
- freetable「查询自定义搜索条件」（写死 `d[0].formName=="aaa"`、`d[0].id==225`）→ 改 HTTP 200 + `$.c=0`；
- PQ「模型专题列表v2」「模型专题标签」（写死 contains obsTopicId/tagId）→ 改 HTTP 200 + `$.c=0`。

## 模式 2：测试数据堆积超业务上限（B2 幂等缺失）

**报错特征**：业务码 `c=-1`、提示含「最多保存 N 个」「上限」；同一用例每次巡检都新增一条数据且从不清理。

**判定**：查该账号下同对象数量（>N）即确认。注意数据**按用户隔离**（ldap/x-qh-id），要按用例实际身份查。

**修复**：
1. 存量清理：用 DELETE 接口 + body（如 `{"formId":<id>}`）清空超限数据；
2. 用例挂**前置 groovy 脚本**「先删后存」：保存前先查询该身份下已有记录 → 逐个 DELETE → 再执行主请求；
3. 脚本带 try-catch 容错（清理失败不影响主请求），验证连续保存后数据恒定 1 条。

**实例**：freetable「保存自定义搜索条件」（ka 对象堆积 21 条超 20 上限）。

## 模式 3：测试数据过期/失效（B3）

**报错特征**：断言期望的固定数据（商品/账号/分类/plan ID）不存在；接口对测试账号返回空或错误。

**判定**：把用例切到有数据的账号/数据重跑，能成功即确认是数据问题而非服务问题。

**修复**：
- 换用有真实数据的账号（如 BGS 授权场景：AAT二号机库全空 → AAT初号机库 39 有 2 商品）；
- 或改数据无关断言；
- **任务型接口注意「对同一目标不可复用」**：授权/创建类任务首次成功后，撤回并不真正移除目标侧数据，再次同目标授权会得到 0——需每次用全新目标/账号或清理目标侧数据，否则巡检必然失败。

## 模式 4：任务锁冲突 / 并发抢占（B4）

**报错特征**：业务码 `c=-1`、提示含「是否有任务在执行中」「请判断是否缺少权限」；用例后置脚本注释含 `unique lock` / `async`。

**判定**：同账号同参数重跑全部成功 → 非权限缺失（若真缺权限重跑必失败），是「任务在执行中」锁冲突；计划内多个用例共用同账号连续执行时互相抢锁。

**修复**：
- 用例前置 groovy 脚本：查锁（调任务列表接口）→ 若有执行中任务则轮询等待（如每 5s 最多 30s）→ 再发起创建；
- 脚本末尾 sleep 错峰；
- 保留后置等待与重试（retryMode=ONLY_NO_RESPONSE）；
- 诚实说明：若无现成查锁接口，查锁部分为「尽力而为」，核心保障是错峰等待+重试。

**实例**：AAT-BGS「ugc import - brand / custom tag」（POST /bgs/ugc/import，unique lock）。

## 模式 5：服务端 500 / 下游服务异常（C 类，不改用例）

**报错特征**：HTTP 500、`An Exception occurred`；或 HTTP 200 但业务码 `c=500`「服务暂不可用」；调用链（callChain）显示下游 RPC `ClientException: code=500->Server Error`。

**判定**：
- 多账号稳定复现 → 服务端异常，非账号/数据问题；
- 全场景（正常/异常/加密/无数据）同报一个错 + 重试仍失败 → 服务级单点故障；
- callChain 里有精确异常位置时直接点名下游服务。

**处理**：**不改用例**（放宽断言会掩盖真实故障）。向用户汇报：
- 具体异常服务（CMDB）+ 接口 + 环境 + traceId 清单；
- 建议：带 traceId 找对应服务团队查日志、核对最近部署（MONITOR_SOURCE 触发往往刚发版）。

**实例**：
- BGS「授权链路」（下游授权任务处理）；floorplan-home「相似方案/相似户型」（下游 recommend-engine RPC 500）；PQ「获取收藏夹标签」（productquery /pq/api/favorites/folder/tags 多账号稳定 500）。

## 模式 6：构建/依赖失败（A 类，修 pom 不改用例）

**报错特征**：任务 `error_reason=JENKINS执行失败`、用例数全 null、Jenkins console `mvn test` 阶段 `BUILD FAILURE` + `Could not resolve dependencies ... Failure to find xxx-SNAPSHOT`。

**判定**：
- console `Finished: SUCCESS` 是假象，看 callback `errorType=3`；
- 依赖缺失需区分**直接 vs 传递依赖**：直接依赖改 pom 版本；传递依赖（由 apollo 测试框架等引入）需 `<exclusions>` 排除 + 显式声明可用版本；
- 到 nexus 验证：缺失版本（404）vs 可用正式版（200）；
- 同一 commit+镜像在 sit 成功、在 fe/oatur 失败 → 环境/节点差异，本地 `.m2` 缓存失败状态未 `-U` 强制刷新。

**修复**：改测试工程 pom → commit 推送（需 gitlab token）。**共享框架缺陷会波及所有依赖它的服务**（单仓库修复只救本服务）。

**实例**：uic-passport/saas-design 测试工程因 apollo 1.9.5/1.8.4 传递依赖 `commons-dbutils:1.7-SNAPSHOT`（nexus 缺失）构建失败。

## 输出要求

对每个失败用例，说明：命中模式编号、判定证据（响应体/重跑对照/调用链）、已做修复 + 验证结果、服务异常时点名服务+traceId+建议反馈对象。未能执行/验证的边界如实说明。
